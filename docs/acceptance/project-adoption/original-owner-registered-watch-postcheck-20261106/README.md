# Registered original-owner watcher postcheck

The staged guard candidate now accepts the original watcher's selection
postcheck as one closed operation. The request binds the plan, source,
context, preparation, state and a 32-character hexadecimal nonce. The
controller rejects aliases with its registration and writable work
directories. It uses the pinned watcher implementation to run
`project-build-verify` and `project-build-input-key` in order. The
selected pointer must match before and after the pair. The controller
holds the nonce-bound event until its final invocation and registration
digest checks pass. A successful guard release requires both calls to
report their terminal ownership and channel proofs.

On Norway, `node --test scripts/test_native_registered_guard_candidate.mjs`
passed all 29 controls. The paired control rejects a missing, unfinished
or extra native call. Node syntax checks and `git diff --check` passed.

The guarded original-owner trial used a 192,000,000-byte reservation.
The guard charged 275,890,176 bytes of conservative growth while setting
up the capsule and recorded exit 75. The supervisor exited 1. That
accounting includes physical-pool changes, so it cannot attribute the
full charge to the staged capsule. The registered postcheck and its
three planned live refusal controls did not start.

An independent read-only review rehashed 1,650 staged files and checked
the full inventory against the manifest. The runtime and native payloads
match the earlier capsule's logical contents. Nine symlink permission
values differ between extractions. Their targets and resolved
containment were checked, and those permission values do not control
writes on Darwin. The only source payload changes are the expected
controller and registrar files.

Recovery preserved the failed guard and released the exact stopped
reservation after three stop inventories, a check of both known process
identities, rehashes of 34 frozen inputs and 2,482 selected files, and a
check of 524 selected directories. The unrelated database retained its
start identity. No files were deleted during recovery.
