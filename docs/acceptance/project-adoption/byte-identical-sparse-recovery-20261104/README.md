# Storage recovery with every image byte preserved
A guarded one-off recovery reduced allocated storage by3,470,786,560bytes (about3.47GB) across three already-closed finished test images. No file was deleted or truncated. Independent review reads all9,123,659,776 logical image bytes and confirms each whole-file SHA-256, inode, size, permissions and owner exactly matches its preimage. All images remain closed and present. Allocation metadata/timestamps can change; byte-identical filesystem metadata is not claimed.

The operation uses [Apple's documented F_PUNCHHOLE interface](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/man/man2/fcntl.2), which preserves file size and returns zeros for deallocated regions. It applies ONLY to freshly re-read, aligned ranges already containing all zeros. Three actual Intel filesystem controls first establish full patterned-fixture preservation/reduced allocation and nonzero/stale-identity refusals. Frozen SDK definitions, zero-range declarations and actual journals underpin the complete-image rechecks. Accounting rules, quota sizes and4GB/500MB/100GB ceilings are unchanged; no data was moved outside accounted roots. This is a bounded recovery, not an installed retention framework.

The earlier512MiB guarded gzip attempt stopped after about600MB conservative growth, leaving a315MB partial archive. The extra global free-space reduction's cause is not established; no verified backup or exact restoration is claimed for that partial archive. Its failure is preserved. Only its stopped reservation was manually recovered after three full process/container observations and final preimage checks. Manual recovery is not an application acceptance pass.

The independent collector initially looked for archived metadata one directory too high. That FileNotFoundError/source is retained privately; only the collector path was corrected to the existing release API's lease subdirectory. It then passed without repeating sparse recovery or any application test.

The unrelated database's start/restart identity stayed unchanged. No service interruption, deletion, installed guard/trust change or parallel activation occurred. The earlier one-image deletion proposal was never approved or executed; it is superseded, and its old allocation/timestamp inventory is stale. The newly available headroom permits a separately guarded configuration-only frontend build; actual admission and build outcome remain separate evidence.
