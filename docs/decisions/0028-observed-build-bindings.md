# Replayable observation bindings and build relations

M4 reuses existing core references/implements/depends-on, required-mapping, unique-target and topology totality/reachability constraints. The versioned build/deployment relation pack adds only compiled-into, produces, packages and starts concepts missing from those existing contracts. Authored meaning remains separate from observed file/tool facts.

The demonstrated gap is nested field/context matching and closed-world selector binding. A mapping/cardinality check alone can accept one arbitrarily chosen Cargo target while omitting another matching target. The built-in build:observation-binding-v1 compares the active referenced target set to every entity matching the explicit targetKind and conditions. Each condition has a component path and exact equals value. Paths traverse entity object fields and array indexes; absent fields never equal null. Comparisons use the native canonical JSON contract, including integral numeric equivalence.

The built-in does not assert existence or uniqueness by itself. The profile must pair it with existing requires-mapping and unique-target obligations. Missing matches, ambiguous matches, omitted matches, wrong fields, unknown parameter/version, cancellation and budget exhaustion cannot supply a successful admitted generation. Its findings are protected from ordinary waivers, and caller callback registries cannot replace it. Native CLI/capture/replay use the compiled evaluator; source bytes are included in the executor identity.

Limits: 128 unique requirement subjects, 64 conditions, component depth 32, component length 256 bytes, 64 KiB per expected value and two million aggregate observation-binding work steps per evaluation. Existing graph/metadata/work controls remain in force. No partial inventory is accepted after a limit.

Source inputs, parser observations, owner correspondence, successful compilation, artifact format/platform, image inspection and runtime observations retain distinct evidence classes. A selector over producer-supplied data is a consistency check, not producer authentication or proof of arbitrary program behavior. Cargo metadata cannot establish compilation; COPY syntax cannot establish final image bytes; EXPOSE cannot establish a listener. Required compiler/image/runtime evidence must arrive from the separate actual tool lanes.

Planned acceptance includes direct Rust controls and actual CLI capture/replay; a real mixed-stack composition with route totality, explicit Cargo package/target/feature context, runtime TOML field binding and Docker artifact/config/launch links; and independently expected positive/refusal mutations. The consumer workspace composer now connects actual Next, Cargo, TOML, file-receipt and Docker providers through the existing process/shard protocol. Its integration matrix is pending execution; this evaluator alone does not establish full M4 or release acceptance. MetaMap compatibility requires a real separately configured evaluator for this new mandatory kind and explicit conversion records; no reference source is edited here.

The read-only match-observations CLI and observation_matches library function reuse the same bounded matcher to propose every matching ID from a structurally checked graph. The supplied constraint is ordinary data. The query performs no policy/active-binding evaluation and creates no admitted state. The consumer driver supplies owned meaning and proposes links; final admission independently rechecks the complete source graph and its active links. This avoids a second field-matching implementation in the orchestration layer.

The files native provider reuses validated workspace input receipts to emit build:input path/digest/byte-length facts for explicitly declared complete nonsecret UTF-8 inputs. Raw bytes remain in the process capture; the emitted receipt is not redaction. Cargo targets expose a normalized discoveryContext containing selected manifests, features/default flags, platform filter, view and owner-root working-directory attribution. That context still explicitly establishes no compilation. These fields support replayable checks without promoting physical tool paths or root-dependent raw metadata into semantic identities.

The source-intent consumer profile is deliberately limited to one owned operation, two declared views, the captured literal Next configuration digest and one named Cargo/Linux/Docker target. Its sixteen explicit requirements bind Next leaves, Cargo identity/context, the listener and Docker packaging/launch syntax. All ordinary Next leaves and RUN instructions require an owned mapping. The native query proposes every matching entity; final admission independently rechecks the complete observed set, mapping cardinality and totality. Generated HTTP bindings retain their earlier native HTTP admission capture; the full composed workspace separately retains its own admission and operation index. Neither capture is an image or execution proof.

The isolated GitHub Linux source job is a CI-specific entry with an explicit four-billion-byte growth check and 500 MB reserve checked between commands. It cannot run on the Intel macOS host, does not impersonate its installed lease and does not change its policy. This source job reports image/browser acceptance pending. It retains positive and failed candidates and logs as artifacts. The existing native Linux regression jobs remain mandatory.

The first consumer profile requires the fixture's empty requested/required Cargo feature sets and its declared x86_64 GNU Linux release target. A target that adds an unselected required feature cannot match the native target requirement. The Linux artifact source and literal Cargo RUN recipe are derived from that one selected Cargo context, rather than unrelated owner strings. The reviewed Next configuration bytes belong to the versioned consumer implementation; updating an owner-side digest alone cannot declare an arbitrary dynamic configuration supported. The frozen negative matrix includes a real Cargo required-feature mutation. General feature discovery remains available through the M1 provider; this consumer profile does not claim every feature/platform recipe.

Next API endpoint entities are governed alongside their route and handler leaves. Their path/method must match the owned operation, and endpoint totality rejects unowned leaves. The build/deployment pack uses the mandatory native relation-pack document envelope; the real process integration gate exercises that deserialization before an acceptance record can exist.
