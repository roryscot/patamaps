# External approval draft

R6 implementation decision, 2026-10-10. This extends the unpublished Draft 1 family; existing MetaMap approvals remain historical evidence and cannot authorize successor outputs. The pinned reference is `GOVERNANCE.md`, `src/governance-model.ts`, `src/governance.ts` and governance tests at `399747a4ad05a37cd8db1cedd53048fad2175be4`.

Deliver a pure `patamaps-governance` crate and file-oriented CLI preparation/verification. A candidate contains up to 16 verified captures with distinct consumer projection specifications and identical graph, packs, policy, context, time and source receipts. Every selected projection must explicitly name the consumer, either through its general consumer field or consistent semantic requirements. Recompute all projections and requested native emissions using the existing evaluator. Emit fixed numeric filenames; candidate identities and locators never become filesystem paths. Complete canonical JSON files and requested Rust/TypeScript source bytes form one addressed inventory. Missing, additional or swapped bytes refuse.

Proposal records bind the complete candidate/baseline, exact inventory, consumer/environment, attributed proposer, deployment or rollback intent, current trust revision/digest, compiler source identity/profile and computed action/fact delta. Attribution confers no permission. Classification covers added/removed/changed graph fields, authority records plus old/new ownership facts, all policy changes excluding redundant graph binding, conservative policy relaxation, budget increases/removal/cost-rule changes, new/changed waivers, exact relation packs, sources, context/time and projection/emission choices. Bootstrap, rollback, authority, policy, relaxation, budget, waiver and law changes require the externally configured owner role as well as matching grants. An ordinary rebind may be approved by an agent only with an explicit matching external grant.

Only externally supplied consumer trust is evaluated. Principals, keys and grants have unique identities; one public key cannot represent independent principals. Each selected grant must cover the action and subject/fact together. `*` alone is a wildcard. Revocation and exact UTC millisecond intervals apply to current supplied time and the entire signed interval. Issue time is inclusive; expiry is exclusive. Current base/trust and all artifact bytes are rechecked; viability waivers cannot suppress these checks.

Signatures cover the entire canonical UTF-8 approval payload, containing fixed domain `urn:patamaps:approval:draft:1`, version and Ed25519 algorithm. Keys are exact canonical base64 Ed25519 SPKI DER; signatures are canonical base64 of exactly 64 bytes. Verification uses pinned `ed25519-dalek` 2.2.0 `verify_strict` and rejects weak/noncanonical public points. This is an intentional tightening of the successor draft; no broad RFC verification-equivalence claim is made. See the [verifier documentation](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict) and [RFC 8032 controls](https://www.rfc-editor.org/rfc/rfc8032#section-7.1). No private signing key or signer is accepted by production APIs.

Ingress/outputs retain the 16 MiB/depth-64/value bounds. Trust permits at most 1,024 principals, 4,096 keys and 4,096 grants, with 128 scopes per grant. Candidates permit 32 requested native emissions. Delta requirements are bounded at 100,000 and scope verification at 2,000,000 checks; exhaustion refuses rather than truncating authorization.

Acceptance needs an independently signed positive control and normative RFC vector, plus forged/readdressed records, weak keys, duplicate identities, reduced requirements, changed bytes, expired/revoked/wrong-scope approvals, interval boundaries, stale trust/base and viable agent self-approval refusal. Execute reviewed native artifacts in an isolated consumer. This pure verifier reports authorization under the supplied context; it does not prove protected host trust or activate a consumer. R7 must obtain trust/base/time from fixed protected installation and repeat verification while holding the native transaction lock.
