# Captured Dockerfile observations

M3 extends the existing discover-native workspace process entry. It parses explicitly supplied complete nonsecret snapshots with tree-sitter-containerfile 0.9.2 and tree-sitter 0.26.5, both MIT, using the published grammar's actual Rust API. The older tree-sitter-dockerfile 0.2.0 package still binds Tree-sitter 0.20 despite a changed dependency on its repository main branch; it is not selected. Pinned Cargo.lock checksums and the workspace executor's source recipe bind the actual parser/provider implementation.

Scope: exact docker/dockerfile:1.10.0 syntax directive on the first line; explicit Linux platform and named selected stage; unique lowercase literal FROM aliases and numeric COPY stage references; declared ARG/ENV values with simple $NAME/${NAME} expansion; literal WORKDIR, local COPY paths and JSON COPY forms; explicit exec-form ENTRYPOINT/CMD; USER and literal EXPOSE declarations. Required constructs outside the supported interpretation remain unresolved. Parsing never executes RUN, project build scripts, Docker, shell code or a frontend.

The configuration declares context, contextFiles, completeContextSnapshot=true, dockerfile, target, platform, frontend and buildArgs. contextFiles must exactly match captured input paths within the context. Completeness is the caller's assertion about its staged snapshot, not live filesystem rediscovery or authentication. The development driver must build and revalidate that coherent inventory; offline reconstruction checks the captured record binding. Supplied raw file bytes remain in captures: field selection/ignore rules are not secret redaction. Binary artifacts need separate identified byte evidence.

Dockerfile-specific ignore files take precedence over the root .dockerignore. The bounded ignore profile supports literal path/descendant rules, optional **/ prefix and ordered negation of those rules. Other wildcard/escape syntax refuses instead of silently adopting Git-ignore semantics. Context COPY observations identify captured members and their byte digests. They do not establish final image bytes, overwrite behavior or arbitrary directory contents from a builder stage. Missing/ignored sources and unresolved stage/argument/working-directory references stay explicit.

RUN effects, remote or archive ADD, shell-form launch commands, other option semantics, non-default escape directives, external contexts and unimplemented instructions are not interpreted as artifact evidence. A COPY --from observation identifies source and destination syntax; the actual compiler/image lane must establish the artifact and its Linux format/platform. EXPOSE establishes no listener or published port. Base image configuration and immutable identity are unavailable until independently inspected.

Bounds: the existing 16 MiB combined input and 1,024 input-file limits, 1 MiB Dockerfile, two-second parser progress bound, 10,000 AST nodes, depth 64, 64 KiB instruction text and 8 MiB aggregate observations. Missing/truncated/unsupported inputs refuse or retain an explicit unsupported finding. Process caching stays disabled.

The [scoped native receipt](../acceptance/cross-stack/m3-docker-observations/receipt.json) records 23 process controls, six native controls and full workspace regression gates. Full M3 acceptance still requires the independent BuildKit lane. Required controls include aliases/index references, COPY/config omissions and ignore precedence, wrong context/target/platform, unresolved ARG, exec versus shell launch, JSON COPY, malformed syntax, parser limits, relocation and captured input identity. Independent BuildKit targets/outline/check results and actual image inspection/runtime are separate required M6 gates. Any disagreement remains unresolved; a native parser pass cannot substitute for Docker.

Primary contracts: [published grammar](https://docs.rs/tree-sitter-containerfile/0.9.2/tree_sitter_containerfile/), [Dockerfile reference](https://docs.docker.com/reference/dockerfile/), [build contexts](https://docs.docker.com/build/concepts/context/) and [Buildx frontend methods](https://docs.docker.com/reference/cli/docker/buildx/build/). This is a bounded application profile, not universal Docker understanding.

Invalid JSON-looking ENTRYPOINT text can fall back to shell form in Docker's [upstream line parser](https://github.com/moby/buildkit/blob/master/frontend/dockerfile/parser/line_parsers.go). The native control requires that case to remain an unsupported/unresolved launch, rather than a valid exec array. A separate missing-image FROM control requires syntax refusal. Both controls and the earlier failed expectation remain retained; the pinned frontend still requires independent BuildKit confirmation.
