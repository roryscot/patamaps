# Protected activation draft

R7 adds a fixed native activator and a separately callable protected reader. The only writable request fields describe a prepared candidate and its external approval. The consumer installs the binary under root control and supplies adjacent `trust.json`; the command accepts no trust/state/clock/program options. A deployment binding inside that trust record identifies the Linux profile, normalized state directory and proposal roots. Its complete bytes are bound by the proposal and approval trust digest. Portable trust records may omit deployment, but persistent activation refuses them.

The first profile requires Linux, root-owned protected ancestors, no-follow descriptor-relative access, regular single-link files, a kernel-held exclusive lock, and a selected local filesystem. The lock lives until the operation returns or dies; owner trust administration must use the same lock. Artifact files and activation manifests are immutable. One pointer replacement publishes the complete generation after file and directory sync and a final current-baseline/trust/clock authorization check. Existing addressed objects are verified before reuse; unreferenced staging data never becomes active by discovery. Consumer reads follow exactly one pointer and verify all bytes and the historical approval.

Exact retries recheck current authorization using the original proposal base and the actual current manifest identity. They do not overwrite state. A different request must bind the actual current baseline. Revocation prevents activation and retry, while retaining historical accepted state. Rollback needs a fresh owner-approved proposal against the current baseline. An error after pointer replacement reports indeterminate and reads protected state for reconciliation. SIGKILL establishes process-interruption behavior, not power-loss durability.

`trust-update` is a separate root-owner administration operation. It acquires the same promotion lock and publishes an immutable adjacent trust file by replacement and directory sync. Changed contents require a new trust revision. Consumer identity, environment, trust identity and deployment layout cannot change through this operation; those require a separately reviewed host migration. The installed service must expose only `activate` to proposers. If a trust-update I/O error occurs after replacement, the owner must reread the protected configuration to determine its actual state.

The selected filesystem allowlist is ext4, XFS, Btrfs, tmpfs and overlayfs. tmpfs and a disposable container overlay can test process interruption but do not establish persistent host power-loss durability. Unknown filesystem types refuse activation.

Acceptance requires real Linux processes and distinct root/proposer UIDs: permission denial against trust/runtime/state/lock/output; complete old/new reads; concurrent stale-base publication; fresh rollback; current expiry/revocation checks; linked files and malformed addressed storage; and kills at locked, artifacts-ready, manifest-ready, precommit and committed. The production binary contains no observation hook. An instrumented integration test executable may pause at these points under its root-owned test harness. macOS explicitly refuses activation and cannot satisfy Linux acceptance. Installation and production adoption remain separate owner actions.

The implementation uses Rust's descriptor-owned file lock ([`File::try_lock`](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock)), safe descriptor-relative operations ([rustix `openat`](https://docs.rs/rustix/1.1.5/rustix/fs/fn.openat.html)), and atomic rename followed by directory sync ([Linux rename](https://man7.org/linux/man-pages/man2/rename.2.html)). The installed executor source identity is not a claim of reproducible binary identity or host trust.
